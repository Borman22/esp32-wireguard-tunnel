# WG Tunnel — контекст для Claude Code

## Что это

ESP32-C3 (и ESP32-S3) как резервный канал доступа к роутеру и локальной сети за ним, когда роутер за NAT:
плата подключается по WiFi к роутеру, поднимает исходящий WireGuard-туннель до VPS и пробрасывает
TCP-порты из туннеля в LAN (веб-интерфейс роутера, SSH). Зачем: если удалённая настройка роутера
сломает его основной VPN-канал, доступ остаётся. Подробности и схема — `README.md`; настройка VPS — `docs/wireguard_server.md`.

## Сборка

```bash
source ~/esp-idf/export.sh   # ESP-IDF v6.0.2
cd <папка проекта>
idf.py set-target esp32c3    # один раз; для S3: rm -rf build sdkconfig && idf.py set-target esp32s3
idf.py build
idf.py -p /dev/ttyUSB0 flash
```

HTML встроен через `EMBED_FILES` — после правки `index.html` нужна пересборка и перепрошивка.
Хост-тест прокси: `test/host_proxy/run.sh` (без железа, под Linux).

## Архитектура

```
main.c → config.c        NVS-настройки + кандидаты WiFi и WireGuard
       → wifi_manager.c  WiFi: STA / AP / APSTA + бесконечный reconnect
       → wg_tunnel.c     супервайзер туннеля, SNTP, откат кандидата
       → proxy.c         TCP-прокси на одном select()
       → web_server.c    HTTP + JSON API
            └ index.html  SPA (Статус, Настройки, Логи)
log_buffer.c  кольцевой лог; b64.c  base64 (Basic Auth, проверка ключей WG)
```

**Порядок инициализации в app_main важен:**
1. `log_buffer_init()` — первым
2. `nvs_flash_init()` → `settings_init()`
3. BOOT-кнопка (`boot_monitor_task`)
4. `wifi_manager_init()` — блокирует до подключения/таймаута
5. `wg_tunnel_start()` — выбирает активную конфигурацию (кандидат/основная), включает SNTP
6. `proxy_start(rules, wg_tunnel_active_config()->address)` — после п.5: нужен туннельный адрес
7. `web_server_start()`

## Критичные нюансы (обязательно читать перед правками)

### Библиотека WireGuard — `esphome/wireguard`, не `trombik/esp_wireguard`
Оригинальная `trombik/esp_wireguard` на ESP-IDF 6.0.2 **не собирается**: GCC 15 с `-Werror`
(`-Wunterminated-string-initialization`, `-Wstringop-overread`) и в mbedtls 4 нет `mbedtls/entropy.h`.
Поддерживаемая ветка `esphome/wireguard ^0.4.8` (тянет `esphome/libsodium`) собирается без правок.
Менять зависимость — только проверив сборку под C3 и S3.

### WireGuard разрешает в туннеле по умолчанию только адрес самого устройства
Без `esp_wireguard_add_allowed_ip()` для всей подсети (`allow_tunnel_subnet()` в `wg_tunnel.c`)
пакеты-ответы на клиентов вроде 10.8.0.3 отбрасываются. Вызывается после каждого `esp_wireguard_connect()`,
потому что `disconnect()` пересоздаёт интерфейс и пира.

### Туннель — НЕ сетевой интерфейс по умолчанию
`esp_wireguard_set_default()` не вызывается намеренно: иначе пакеты WireGuard до сервера пошли бы
в сам туннель. Весь прочий трафик (NTP, DNS, UDP до сервера) идёт через WiFi.

### Время обязательно
Рукопожатие содержит метку TAI64N; с неверными часами сервер его отвергает. RTC нет, поэтому время
берётся из SNTP (`pool.ntp.org`, `time.google.com`) или из браузера (`POST /api/time`, принимается
только пока часы не установлены). Супервайзер не создаёт туннель, пока `time() < WG_MIN_VALID_EPOCH`.
`CONFIG_LWIP_SNTP_MAX_SERVERS=2` — без этого `ESP_NETIF_SNTP_DEFAULT_CONFIG_MULTIPLE(2, …)` не сработает.

### Откат кандидата WireGuard (`wg_pend`)
Если основная конфигурация туннеля уже настроена, изменение через веб идёт в `wg_pend`, а не в `app_cfg`.
При следующей загрузке `wg_tunnel_start()` берёт кандидата и ставит `s_trial`. Таймер `WG_TRIAL_TIMEOUT_S`
запускается, когда у туннеля впервые появилась возможность подняться (есть WiFi **и** время), а не с
момента загрузки — иначе недоступность WiFi откатывала бы исправный кандидат. Рукопожатие → `settings_promote_pending_wg()`;
таймаут → `settings_clear_pending_wg()` + `esp_restart()`.
Первая настройка (основной конфиг пуст) пишется сразу в `app_cfg`.
GET /api/settings возвращает **кандидата**, если он есть (это то, что пользователь ввёл последним).

### Бюджет сокетов lwIP — ровно 16 (жёсткий максимум)
httpd: `HTTP_MAX_OPEN_SOCKETS`(2, `lru_purge` включён) + 3 служебных; прокси: `PROXY_MAX_RULES`(3) слушающих + 2×`PROXY_MAX_CONNS`(4).
`_Static_assert` в `web_server.c` ловит превышение при компиляции. Хочется больше соединений —
уменьшать число правил или открытых сокетов httpd, `CONFIG_LWIP_MAX_SOCKETS` больше 16 не поднять.
Весь прокси живёт в одной задаче на `select()`, буферы статические (`PROXY_BUF_SIZE` × 2 × `PROXY_MAX_CONNS`).

### Светодиод состояния (`status_led.c`)
Задача опрашивает каждые 50 мс `wifi_manager_is_connected()` и `wg_tunnel_get_state()`: нет WiFi: погашен; WiFi есть и
состояние не `WG_STATE_UP`: вспышки; `WG_STATE_UP`: горит. Для частого опроса добавлена `wg_tunnel_get_state()`
(просто возвращает `s_state`): `wg_tunnel_get_status()` для этого не годится, она каждый раз спрашивает у
библиотеки время рукопожатия. Вывод и полярность в `board_config.h`: C3 это GPIO8 active-low (strapping pin, но
после старта им можно управлять, как и на плате BMS), S3 это GPIO48 active-high. Полярность S3 в тесте мигания не
проверялась (мигание выглядит одинаково при обеих), поэтому при инверсии менять `BOARD_LED_ACTIVE_LEVEL`.

### Кнопка перезагрузки: две постоянные + одна условная
`POST /api/restart` (под авторизацией) вызывается из `restartDevice()` в `index.html`. Постоянные кнопки «Перезагрузить плату»
на «Статусе» и в «Настройках» идут через `confirmRestart()` (диалог подтверждения). Красная кнопка «Перезагрузить сейчас»
под «Сохранить» показывается только когда сохранённые настройки требуют перезагрузки, подтверждения у неё нет. После запроса
страница не обновляется вслепую: ждёт 5 с, потом опрашивает `/api/status` каждые 2 с (до 3 минут) и обновляется, когда плата
ответила. Через туннель возврат занимает 20-40 с (WiFi, SNTP, рукопожатие).

### Прокси слушает на всех интерфейсах, но принимает только туннельный адрес
После `accept()` проверяется `getsockname()`: локальный адрес должен совпасть с туннельным IP платы,
иначе соединение закрывается. Так прокси не зависит от пересоздания туннельного netif и недоступен
из локальной сети и из AP. Соединение закрывается, только когда закрылись обе стороны (поддержан half-close);
если одна сторона закрылась, а вторая молчит — через `PROXY_HALF_CLOSE_TIMEOUT_S` (слотов всего четыре).

### Нет свободного слота: очередь, а не отказ
Слушающие сокеты не попадают в `select()`, пока нет свободного слота и нечего вытеснить
(`slot_available_or_evictable`): ожидающие клиенты стоят в очереди lwIP (`PROXY_LISTEN_BACKLOG`).
Отказ с немедленным `close()` ломал загрузку страниц TP-Link: он закрывает соединение после каждого ответа,
а браузер открывает по шесть новых сразу. Если все слоты молчат дольше `PROXY_EVICT_IDLE_S`, `accept_client()`
вытесняет самое давнее. Для четырёх соединений нужен `CONFIG_LWIP_MAX_ACTIVE_TCP=32` (по два PCB на соединение).

### Версия компонента `driver` в IDF 6
`driver/gpio.h` в IDF 6 живёт в `esp_driver_gpio`; в `REQUIRES` `main/CMakeLists.txt` указан именно он.

### BOOT-кнопка — нельзя проверять при старте
GPIO9 (C3) и GPIO0 (S3) — strapping pins: LOW при сбросе уводит чип в загрузчик. Кнопка опрашивается
в `boot_monitor_task` во время работы; 3 с → `settings_reset()` + `esp_restart()`. Номер пина выбирается
в `board_config.h` по `CONFIG_IDF_TARGET_*`.

### Лог-буфер — spinlock, не мьютекс
`log_buffer.c` использует `portMUX_TYPE`: хук `esp_log_set_vprintf` вызывается из любого контекста
(WiFi/lwIP-задачи, прерывания), где мьютекс FreeRTOS вызвал бы дедлок. Форматирование — до захвата
спинлока, внутри только `memcpy`.

### Точка доступа закрыта WPA2
AP закрыта паролем `WIFI_AP_PASSWORD` (`wifi_manager.h`): через страницу
меняются ключи VPN, а в APSTA точка остаётся доступной постоянно. Секретом пароль не считается.

### Энергосбережение WiFi выключено (`WIFI_PS_NONE`), канал только 20 МГц (`WIFI_BW20`)
Питание от сети, а входящие пакеты из туннеля не должны ждать пробуждения радио.
Ширина канала ограничена 20 МГц: точка доступа роутера раздавала 40 МГц, и на слабом сигнале (около -76 dBm)
это давало 14% потерь и 15-25 КБ/с. После перехода на 20 МГц потери 3%, а один поток 80 КБ/с (с хорошим
сигналом, окнами TCP 11520 и записью сразу после чтения до 190-200 КБ/с). Константа в IDF 6: `WIFI_BW20`
(`WIFI_BW_HT20` удалена). Значения `wifi_phy_mode_t`: 0=LR 1=11B 2=11G 3=11A 4=HT20 5=HT40 6=HE20 7=VHT20.

### Нельзя закрывать сокеты после `shutdown(SHUT_WR)` (half-close выключен: `PROXY_HALF_CLOSE=0`)
На lwIP из ESP-IDF 6.0 соединения, закрытые после `shutdown(fd, SHUT_WR)` и зависшие в FIN_WAIT, приводили
к порче кучи (`tcp_slowtmr -> tcp_free`, `tlsf_free assert`). Воспроизводилось обрывом множества соединений
(`curl --max-time 0.4` по 200 штук) и ожиданием 30+ с. Причина в lwIP не установлена, помогли два изменения:
прокси закрывает оба сокета сразу, как только одна сторона закрылась и её данные доставлены, и короткие
`CONFIG_LWIP_TCP_MSL=3000` / `CONFIG_LWIP_TCP_FIN_WAIT_TIMEOUT=5000` (по умолчанию TIME_WAIT держится 2 минуты,
`MAX_ACTIVE_TCP=32`, и lwIP постоянно убивает старые PCB). Хост-тест `run.sh` собирает прокси с
`-DPROXY_HALF_CLOSE=1`, потому что проверяет half-close; на железе он выключен.

### Библиотека WireGuard и lwIP из IDF 6.0: две поправки в сборке
- `CONFIG_ESP_NETIF_BRIDGE_EN=y` + `CONFIG_LWIP_NUM_NETIF_CLIENT_DATA=1`: иначе `netif_callback_fn` в esp_netif
  принимает `netif->state` туннельного интерфейса за `esp_netif_t` и падает (`Load access fault` в
  `esp_netif_internal_dhcpc_cb` при создании туннеля). Включается `LWIP_ESP_NETIF_DATA`.
- `add_compile_definitions(CONFIG_WIREGUARD_MAX_SRC_IPS=4)` в корневом `CMakeLists.txt`: по умолчанию у пира
  один слот разрешённых адресов, он занят адресом самого устройства, и `allow_tunnel_subnet()` падал с
  `ERR_MEM` (подсеть не разрешалась, пакеты клиентов отбрасывались).

### Прокси: при нехватке слотов клиент ждёт в очереди, а не получает отказ
Слушающие сокеты не попадают в `select()`, пока нет свободного слота и нечего вытеснить
(`slot_available_or_evictable`). TP-Link закрывает соединение после каждого ответа, браузер открывает по шесть
новых сразу: отказ ломал загрузку страницы. Если все слоты молчат дольше `PROXY_EVICT_IDLE_S` (15 с),
`accept_client()` вытесняет самое давнее. Запись сразу после чтения (без второго `select()`) и окна TCP 11520
подняли скорость с 116 до 196 КБ/с на один поток.

### Прокси к веб-интерфейсу TP-Link: что надо знать
- HTTPS-сервер роутера старый: curl на OpenSSL 3 требует `OPENSSL_CONF` с `Options = UnsafeLegacyServerConnect`.
- У роутера включена проверка заголовка `HTTP Referer`: без неё отключения скрипты возвращают `403`, а страница
  остаётся белой. Прокси прозрачный (TLS сквозной), заголовки подменить не может. Лечится в роутере: отключить
  «Проверка заголовка HTTP Referer» (на домашнем C80 после этого `https://<плата>:8443` заработал).
- Порт 80 роутера отвечает редиректом на HTTPS, отключить HTTPS для локального управления нельзя.
- Страница роутера состоит из ~73 запросов, каждый на новом TLS-соединении: 24-43 с вместо 6-8 с напрямую.
  Процессор платы при этом простаивает (>85%), узкое место: слабый HTTPS-сервер роутера и ёмкость радиоканала.

## WiFi — режимы и логика

Подробно — README, «Режимы работы WiFi»:
кандидат (`wifi_pend`) → сохранённая сеть → AP/APSTA; после первого IP переподключение бесконечное, с паузой `RECONNECT_DELAY_MS` (5 с) через одноразовый `esp_timer`
(в обработчике событий нельзя блокировать общую задачу событий); причина обрыва логируется один раз при потере связи;
`start_sta()` в начале сбрасывает `s_retry` и event bits (иначе второй вызов видит старый `WIFI_FAIL_BIT`).

## NVS-пространства имён

| Namespace   | Что хранит |
|-------------|------------|
| `"app_cfg"` | `wifi_ssid/pass`, `auth_user/pass`, `wg_*` (priv, pub, psk, endpoint, port, addr, mask, keepalive), `px{0..2}_{lp,ip,tp}` |
| `"wifi_pend"` | кандидат WiFi: `ssid`, `pass` |
| `"wg_pend"` | кандидат WireGuard: те же ключи `wg_*` + флаг `valid` |

Имена ключей NVS ≤ 15 символов. `load_*` молча оставляют значение по умолчанию, если ключа нет
(поле добавили в новой версии — после OTA старые настройки не пропадают).

## HTTP API

| Метод | Путь | Описание |
|-------|------|----------|
| GET | `/` | index.html |
| GET | `/api/status` | WiFi, туннель (состояние, возраст рукопожатия, trial), прокси, система |
| GET | `/api/settings` | настройки; секреты только как `*_set: bool`; `wg_pending`, `max_rules` |
| POST | `/api/settings` | частичное обновление; ответ `{ok, restart_required, wg_pending}`; ошибка валидации — 400 с текстом |
| GET | `/api/wifi/scan` | кэш WiFi-сетей, снятый при старте |
| GET | `/api/logs?from=N` | `{logs:[{seq,msg}], next, uptime_ms}` |
| POST | `/api/time` | `{"epoch":N}` |
| POST | `/api/restart` | перезагрузка через 500 мс |
| POST | `/api/ota` | бинарный образ → OTA + reboot |

Валидация только на границе (`web_server.c`): ключи WG — 44 символа base64 → 32 байта (`b64_is_wg_key`),
IPv4 через `inet_pton`, порты 1–65535, порт прокси ≠ 80 и без дублей. Любое изменение WiFi/WG/правил
прокси требует перезагрузки (`restart_required`), остальное действует сразу.

## Что проверено, а что нет

- Проверено: сборка под ESP32-C3 и ESP32-S3 без предупреждений; `test/host_proxy/run.sh` (прокси: целостность
  5 МБ в обе стороны, half-close, лимиты, параллельность, отказ чужим; ASan+UBSan чисто); JS страницы
  проходит `node --check`.
- Проверено на железе (ESP32-S3, 160 МГц): WiFi, туннель до OpenWrt, SNTP, прокси к домашнему C80 и к OpenWrt,
  стабильность под 300 короткими HTTP-запросами, 4x300 КБ с проверкой SHA-256, 200 обрываемых TLS-соединений.
- **Не проверено на железе:** OTA, откат кандидата WireGuard, работа на ESP32-C3 с этими настройками, дача.
  Порча кучи искалась с `CONFIG_HEAP_POISONING_COMPREHENSIVE=y` (закомментировано в `sdkconfig.defaults`).

## Стиль кода

- Комментарии на русском языке
- Без лишних комментариев — только когда WHY неочевиден
- Без абстракций «на будущее» — только то, что нужно сейчас
- Валидация только на границах системы (HTTP-вход, NVS-чтение)
- Не добавлять обработку ошибок для невозможных сценариев
- Код разбит по модулям `.c/.h`; в `.h` — документация API, в `.c` — пояснения реализации
